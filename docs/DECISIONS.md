# Decisions

Status: living document — updated 2026-11-20. Items marked open or awaiting review below are still unresolved.
**Confirmed** = agreed by the product owner. **Proposed** = technical recommendation awaiting review. **Open** = unresolved question.

## Confirmed

| ID | Decision |
|---|---|
| D-01 | Single therapy center. No multi-center functionality. |
| D-02 | One operator: the center administrator manages everything. One administrator account in the MVP. |
| D-03 | Therapists have **no accounts**, never log in, never confirm sessions, never manage patients or documents. |
| D-04 | Stack: Python 3.12, FastAPI, SQLite + SQLAlchemy 2.0 + Alembic, React + TypeScript + Vite + Tailwind, python-docx + lxml, LibreOffice headless, Greek public holidays support. No Redis, Docker or task queues. |
| D-05 | Local-first: runs on one center computer. Storage outside the Git repository. Real patient data, templates, signatures, stamps and license details are never committed. |
| D-06 | Multiple predefined DOCX templates (≈ 6–7+), each for one exact therapy/therapist combination, containing its fixed text, therapist details, signatures and stamps. Shared across patients. |
| D-07 | Template selected by **exact** combination match; no match or multiple active matches is an error, never a guess. Templates are validated before activation, versioned, never overwritten. |
| D-08 | Prescribed counts, planned dates and evidence of performed sessions are distinct concepts. The application never claims scheduled dates prove sessions were performed. |
| D-09 | Session counts come only from the doctor's prescription, entered manually by the administrator in the MVP; the application never invents them. |
| D-10 | (extended by D-35) Future: prescription text → extracted proposal → administrator review/correction → save. Designed for now, **not implemented** (no AI/OCR in the MVP). |
| D-11 | Scheduling rules: no weekends, no Greek public holidays, exact prescribed count, prefer ≥ 1 day gap (soft), ≤ 2 distinct therapists per patient per day (same therapist counts once), even distribution, conflicts reported, never silently invalid. At most one session per therapy per day, configurable. The administrator reviews and adjusts dates. |
| D-12 | No therapist confirmations or per-session completion workflow in the MVP. |
| D-13 | Document is created after the period ends; issue date = date of generation; DOCX + PDF; preview before issuance. |
| D-14 | Issued documents are immutable; each references its exact template version and keeps a snapshot of all data used; corrections create new versions. |
| D-15 | Home visit ΝΑΙ/ΟΧΙ is chosen per therapy per period, stored, editable until issuance. |
| D-16 | ΑΔΑ and representative name are center-level settings. The "ΔΕΙΓΜΑ" watermark is removed from generated documents only. |
| D-17 | The spike is preserved unchanged with its tests; validated DOCX-to-PDF prototype approved. |
| D-18 | Cross-patient therapist conflicts are out of scope for the MVP. |
| D-19 | Prescription structure (from a real EOPYY "Γνωμάτευση Παροχών ΕΚΠΥ", 2026-11-20): an **overall validity** (e.g. 16/09/2025–15/03/2026) and, per therapy, a **monthly quantity** (e.g. speech 8, child psychotherapy 6). The quantities are per month, not totals for the whole validity. |
| D-20 | Each therapy's validity is split into **monthly referral periods** (page 2 of the prescription), e.g. 16/09–15/10, 16/10–15/11, … 16/02–15/03. These are modelled separately from the prescription's overall validity. |
| D-21 | Document periods follow the referral windows and need not match calendar months (e.g. 16th to 15th). Each document is tied to its monthly period and that period's quantities. |
| D-23 | A single prescription may contain therapies with **different referral-period dates or durations**. Each therapy has independent referral periods; the system never assumes all therapies share identical monthly windows (2026-11-20). |
| D-24 | A therapy with **zero** session dates in a document period is a strict validation error: no attestation is ever generated for a therapy without session dates (2026-11-20). |
| D-25 | Center-level fields (ΑΔΑ, representative) are mapped either as **dynamic** — the value must come from the center settings, and generation fails with a clear error when it is missing — or as **static** — the template's own text is kept and a supplied value is refused. The mode must be stated explicitly in the mapping; template text is never silently kept for a dynamic field (2026-11-20). |
| D-26 | ~~One five-section template serves any subset of its sections~~ — **superseded by D-28** (2026-11-21). | 
| D-27 | Every therapist detail the template prints (licence number, issuing authority, licence date and, when printed, the name) is checked against the therapist's record, ignoring case, accents and spacing; a mismatch, or a detail missing from the record, makes the version invalid. Signatures and stamps cannot be verified automatically: sections without any image are flagged, and their identity is confirmed by the administrator in the preview (resolves U-12, 2026-11-21). |
| D-28 | The center provides **three** therapies — speech therapy, psychotherapy, occupational therapy — with exactly one therapist each (not special education, not physiotherapy). It keeps **seven** templates, one per non-empty combination, each with only its own sections and the corresponding therapists' static details, signatures and stamps. Matching is **exact**: the requested (therapy, therapist) pairs must equal a template's configured pairs — never a larger or smaller template, never another therapist; every section of the matched template is filled. During development the seven templates are **synthetic TEST ONLY** documents with fictional therapists; they will be replaced by the center's real templates. The center's therapies, therapists and templates are data entered by the administrator, not code (2026-11-21). |
| D-22 | The model must stay extensible: other prescription layouts or treatment-duration rules may exist; no future prescription is assumed to look exactly like the example. |
| D-29 | **M5.0 (approved 2026-11-20).** Administrator sessions are server-side rows (`admin_sessions`, migration `0003_admin_sessions`) storing only SHA-256 hashes of the session token and the CSRF token. Idle timeout 30 min and absolute lifetime 12 h, checked independently. |
| D-30 | The application binds to **loopback only** and refuses to start on any other address; LAN access would need an explicitly configured and validated TLS setup and is not implemented. |
| D-31 | Passwords are hashed with Argon2id (`argon2-cffi`). The administrator is created and its password changed **only through the CLI**; there is never a web setup endpoint and never default credentials. |
| D-32 | Login uses progressive backoff (from the 5th consecutive failure, 30 s doubling up to 15 min), a CSRF synchronizer token for every unsafe protected request, Origin/Host validation and no CORS; failures never reveal whether a username exists. The Vite dev proxy keeps one origin. |
| D-33 | Every API route requires the administrator session unless it is on an explicit public allow-list (`/api/health`, login, session status). A structural test inspects each route's effective dependencies recursively, including router-level ones. |
| D-34 | **M5.1 (approved 2026-11-21).** Therapy types and therapists are never hard-deleted (no DELETE endpoints): they are deactivated. A therapy type's `code` is immutable once anything references it. A therapy type or therapist used by an **active** template cannot be deactivated, and a therapist's identity fields (`full_name`, `license_no`, `license_authority`, `license_date`) cannot change while an active template uses them; the administrator must first deactivate the template, change the data, and upload/activate a corrected version through the existing template lifecycle. Template matching refuses inactive therapy types or therapists even for an active template. |
| D-35 | **Permanent future requirement:** automatic reading of EOPYY prescriptions/referrals from PDFs or images (OCR/AI). Not built in M0–M5.1. Required properties: the uploaded source and the raw extracted values keep their provenance; extracted values are mapped to internal therapy types and entities; the original document is shown beside the extracted data for review; uncertain or unmatched fields can be corrected; **only after explicit administrator confirmation** may authoritative patient, prescription, period or schedule data be created or changed — unverified output never writes authoritative records. Consequences already honoured: `prescription_items.eopyy_code` keeps the printed/source code and is independent of `therapy_types.code`; `therapy_types.eopyy_code` is only a mapping aid, and several codes per therapy type may later be added as an additive mapping table without breaking current records. Supersedes the narrower wording of D-10. |

Therapist assignments stay separate. ## Superseded by the confirmed workflow

These items from the earlier architecture proposal no longer apply:

| Earlier proposal | Replaced by |
|---|---|
| Roles `admin` / `staff` / `therapist`; `users.therapist_id` | One `admin_account` (D-02, D-03) |
| Therapists confirm their own sessions; `sessions.status = confirmed`, `confirmed_by` | Administrator adjusts and approves the schedule; no per-session confirmation (D-12) |
| "Only confirmed completed sessions appear in an issued document" | Documents use approved schedule dates; no claim that they prove performance (D-08, D-13); legal requirement to be verified (Q-01) |
